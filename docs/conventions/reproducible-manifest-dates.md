# Reproducible Manifest Dates

A workflow-run or derived-dataset manifest (`datapackage.json`, run record, provenance manifest)
records *when the run happened*. If the rule that writes it stamps `created` / `updated` with the
**regeneration wall-clock** — `date.today()` / `datetime.now()` — then re-running the rule for any
unrelated reason rewrites that date to "now". Two things break:

1. **Date honesty.** A 2026-05-04 baseline silently becomes 2026-05-30 on a no-op rebuild. The
   manifest now misrepresents when the underlying run actually occurred.
2. **Byte-reproducibility.** The committed manifest can no longer be regenerated byte-for-byte, so you
   cannot verify a regeneration by `git diff` — the date field always drifts. A clean rebuild looks
   dirty, which trains reviewers to ignore manifest diffs.

## The convention

**Manifest `created` / `updated` must derive from the run's identity, not from regeneration
wall-clock time.** In order of preference:

1. **Run-identity date** — the date already encoded in the run's slug/id (e.g. a `run_slug` of
   `2026-05-04-cohort-assemble` carries its own date). Parse it from the identity; do not re-stamp.
2. **Explicit `--produced-at`** — a CLI/config parameter the caller passes, defaulting to the run
   identity, so a deliberate re-date is explicit and auditable rather than incidental.
3. **Source/commit time** — the authoring git-commit time of the inputs or recipe, when neither of
   the above is available.

Never `date.today()` at write time for a field that is supposed to describe the *run*, not the
*rebuild*. (A genuine `generated_at` / `build_time` field, if you want one, is a *separate* field
explicitly documented as non-reproducible and excluded from diff-based verification — do not overload
`created` / `updated` with it.)

## Worked defect (cancer-evolution)

Both `cohort_assemble_t007` (cohort `datapackage.json`) and the `t007-gates` `run_datapackage` rule
set `created` / `updated` via `date.today()` / `date.today().isoformat()`. Re-running a rule to fix an
unrelated field (e.g. removing a path-escaping resource) rewrote the run date from a 2026-05-04
baseline to the 2026-05-30 wall-clock. Landing a clean fix required a force-run followed by a manual
restore of the honest date — exactly the friction this convention removes. The defect is the same in
all four chains in that project, so the fix generalizes.

## Relationship to other conventions

- The pipeline-audit playbook's axis-2 *minimum workflow contract* calls for a manifest/datapackage
  when outputs feed later analyses; this convention specifies how that manifest must date itself.
- It is a workflow/DAG-level reproducibility property, adjacent to the single-writer /
  output-ownership discipline in
  [`../process/pipeline-audit-and-refactor.md`](../process/pipeline-audit-and-refactor.md): both are
  about manifests and rules being honest about provenance rather than incidental to run order.
